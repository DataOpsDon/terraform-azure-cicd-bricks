# Terraform CI/CD for Azure (GitHub Actions)

Shared, versioned GitHub Actions templates for deploying Terraform to **Microsoft Azure**.
Stack repositories consume this repo through a small caller workflow, so pipeline logic
lives in one place and is upgraded by bumping a tag.

This repo is scaffolded by `ign init-cicd-repo`; consuming repos are scaffolded by
`ign init --cloud azure --cicd github`.

---

## Repository structure

```text
.github/
├── actions/
│   ├── tf-ci/action.yaml        # OIDC login, init, fmt, validate, Checkov (+ SARIF upload)
│   ├── tf-plan/action.yaml      # OIDC login, init, plan, upload plan artifact, PR comment
│   └── tf-apply/action.yaml     # OIDC login, init, download plan artifact, apply
└── workflows/
    ├── _terraform-pipeline.yml  # Reusable workflow: CI -> Plan -> (approval) -> Apply
    └── release.yml              # Semantic version tags + GitHub releases on merge
CODEOWNERS
README.md
```

## Pipeline flow

| Job | GitHub environment | Identity | Runs when |
|---|---|---|---|
| `Terraform-CI` | `<environment>` | build (Reader + state blob access) | always |
| `Terraform-Plan` | `<environment>` | build | after CI |
| `Terraform-Apply` | `<environment>/apply` | deploy (Owner, constrained) | push to a ref in `apply_on_refs` (default `main`, `develop`) — never on PRs |

Add **required reviewers** to the `<environment>/apply` environment to get a manual approval gate
before apply. The apply job uses the exact plan file produced (and reviewed) in the plan job.

## Authentication — OIDC, no secrets

Each job logs in with [`azure/login`](https://github.com/Azure/login) using workload identity
federation, and exports `ARM_USE_OIDC` / `ARM_USE_AZUREAD` so the `azurerm` provider **and** the
`azurerm` state backend authenticate with the same token. Two user-assigned managed identities are
expected, each with a federated credential for the consuming repo:

| Identity | Federated credential subject |
|---|---|
| Build | `repo:<org>/<repo>:environment:<environment>` |
| Deploy | `repo:<org>/<repo>:environment:<environment>/apply` |

`ign bootstrap` (with `cicdPlatform: github`) creates both identities, the federated credentials,
role assignments and the state storage account.

## Configuration in the consuming repo

Set these as **environment variables** on both the `<environment>` and `<environment>/apply`
GitHub environments (or pass the equivalent workflow inputs):

| Variable | `<environment>` value | `<environment>/apply` value |
|---|---|---|
| `AZURE_CLIENT_ID` | build identity client ID | deploy identity client ID |
| `AZURE_TENANT_ID` | tenant ID | tenant ID |
| `AZURE_SUBSCRIPTION_ID` | target subscription | target subscription |
| `TF_STATE_SUBSCRIPTION_ID` | state subscription | state subscription |
| `TF_STATE_RESOURCE_GROUP` | state resource group | state resource group |
| `TF_STATE_STORAGE_ACCOUNT` | state storage account | state storage account |
| `TF_STATE_CONTAINER` | state container | state container |

Optional repository secret `MODULE_REPO_PAT`: a token with read access to private Terraform module
repositories, used to authenticate `git::https://github.com/...` module sources during `terraform init`.

The consuming repo must contain the `Makefile` and `templates/scripts/tf-*.sh` scripts generated by
`ign init` — the composite actions call `make tf-install`, `make tf-init`, `make tf-plan`, etc.

## Example caller workflow

```yaml
name: network

on:
  push:
    branches: [main, develop, 'feature/**']
    paths: ['stacks/network/**']
  pull_request:
    branches: [main, develop]
    paths: ['stacks/network/**']

permissions:
  id-token: write
  contents: read
  pull-requests: write
  actions: read
  security-events: write

jobs:
  dev:
    if: (github.event_name == 'pull_request' && github.base_ref == 'develop') || (github.event_name != 'pull_request' && (startsWith(github.ref, 'refs/heads/feature/') || github.ref == 'refs/heads/develop'))
    uses: dataopsdon/terraform-azure-cicd-bricks/.github/workflows/_terraform-pipeline.yml@v1.0.0
    with:
      working_directory: stacks/network/terraform
      environment: dev
    secrets:
      module_repo_pat: ${{ secrets.MODULE_REPO_PAT }}
```

### Reusable workflow inputs

| Input | Required | Default | Description |
|---|---|---|---|
| `working_directory` | yes | | Terraform root module directory |
| `environment` | yes | | Environment name; selects `tfvars/<environment>.tfvars` |
| `apply_environment` | no | `<environment>/apply` | GitHub environment for the apply job |
| `apply_on_refs` | no | `["refs/heads/main","refs/heads/develop"]` | Refs allowed to apply |
| `azure_client_id` / `azure_deploy_client_id` | no | `vars.AZURE_CLIENT_ID` | Build / deploy identity |
| `azure_tenant_id`, `azure_subscription_id` | no | `vars.AZURE_*` | Tenant and target subscription |
| `state_subscription_id`, `state_resource_group`, `state_storage_account`, `state_container` | no | `vars.TF_STATE_*` | azurerm backend |
| `state_key` | no | `<working_directory>/<environment>.tfstate` | State blob name |
| `terraform_version` | no | `1.12.2` | Terraform CLI version |
| `checkov_skip_check` | no | `''` | Comma-separated Checkov IDs to skip |
| `checkov_soft_fail` | no | `true` | Don't fail on Checkov findings |

## Releasing

`release.yml` tags every merge: `main` produces `vX.Y.Z`, `develop` produces `vX.Y.Z-rc.N`.
Add `#major` / `#minor` / `#patch` to the merge commit message to control the bump (default patch).

The reusable workflow references its own composite actions with a literal ref
(`dataopsdon/terraform-azure-cicd-bricks/.github/actions/tf-ci@main`) because `uses:` cannot take an
expression. When you change an action, cut a release and bump that ref (use a full commit SHA if
your organisation requires it). Consumers then bump the tag in their caller workflows.

## Repository settings checklist

- **Settings → Actions → General → Access**: allow access from repositories in the organisation,
  so consumers can call the reusable workflow and composite actions.
- Protect `main` and `develop`; require PR review and CODEOWNERS approval.
- Update `CODEOWNERS` with your platform team.
